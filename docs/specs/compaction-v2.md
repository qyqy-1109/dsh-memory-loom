# 压缩循环 v2 规格（总结 → 当作记忆 → 再总结）

- 状态：方案，待拍板
- 日期：2026-11-10
- 现状：`#compact` 由 `active.length >= compactAt(1200)` 触发。真库活跃 220，**从来没触发过**，
  所以摘要层只有 11-06 测试留下的一条孤儿（「版本进展」，11 条成员全 archived）。

---

## 0. 目标改法

把"到 1200 条才压"改成"**同一件事重复到一定量就压**"，并给循环装四道闸。

---

## 1. 触发判据：从库存量改到冗余度

### 现在的问题

按总条数触发 = 按库存量决定要不要压缩。库一小就永远不响（现在就是），
库一大就一次性大扫除。这跟 df≤2 那个教训同源：拿绝对数量当阈值，尺度一变就失效。

### 改法

- 去掉 `active.length < compactAt` 这个总门槛。
- 候选池：可淘汰活跃条目（`EVICTABLE` 且非 `explicit`）里**权重尾部**
  （沿用 `compactKeepRatio`，保护权重最高那一截不被吸走）＋**最近 W 条新写入**。
- 判据交给已有的聚类：`planSummaries` 里出现 size ≥ `summaryMinMembers`(默认 6) 的簇，就压。
- 冷却保留并加强：距上次超过 `compactCooldownMs`(建议 10 分钟) **或**新增 ≥ `compactDelta`(建议 20 条)
  才跑一次聚类。聚类要遍历，不能每写一条都跑。
- 一次最多压 `summaryClusterLimit`(4) 组，防一次性大扫除。

**代价**：写路径偶尔多一次 O(n·簇数) 的聚类。按 2000 条实测的检索耗时为参照，可接受；
冷却参数封住最坏情况。

## 2. 闸一：摘要必须能落回原文（指针不断）

- `members: [id]` 已有。
- **真改动**：被摘要覆盖的成员，**永久豁免归档物理修剪**（`#trimArchive` 跳过 `summaryBy != null` 的行）。
  现在的 `maxArchive` 会物理删最老的归档，删掉之后摘要就指着空气。
- `restore`（撤销归纳）已有；撤销后成员回活跃，摘要删除。

## 3. 闸二：两代封顶

- 摘要**不参与再压缩**。现在天然如此（候选池来自 `memories` 且限 `EVICTABLE` = fact/self/episode）。
- 把这条写成**测试**，而不是靠"现在刚好这样"：断言 `summaries` 里的行不会进候选池，
  且 `EVICTABLE` 集合里没有 `summary`。以后谁想加，测试会红。
- 想再往上压（L3），必须人工显式发一次，工具里单独一个 action，不进自动流程。

## 4. 闸三：压的时候留下"例外"

最值钱的往往是"但有一次例外"，而它最容易被压掉。

- 聚类后逐条校验：与簇主题相似度低于门槛的成员，**从 `members` 里剔除**，留在活跃。
- 极性相反的（"喜欢深色" vs "不喜欢深色了"）一律不进同一摘要 —— 已有 `similarity` 的极性判断可复用。
- 摘要文本里保留一句"另有一条例外"的线索：只记 id，不写正文（正文还在库里）。

### 4.1 实测修正（0.64.0）

第一版这块判死了所有簇，真库一条摘要都压不出来（事件里全是 `summary.skip-outliers`）。两个错：

1. **基准错了**：拿每一条去跟 `plan.text`（关键词拼接）比。那段文本跟原文的字面重合天然低，
   于是人人都"离群"。改成跟簇的 **medoid**（与簇内平均最像的那条）比 —— 簇内互比才对。
2. **判据错了**：用绝对地板 0.18。真库里同簇两两相似度只有 **0.08–0.26**（IDF 覆盖率压得低），
   绝对地板等于把整簇判死。改成**相对**：比簇内中位数差一半以上的算离群，再垫 0.05 硬地板防全灭。

修正后真库副本实测：**压出 3 组、归档 28 条**。

## 6. 指标

三个数，都能量：

| 读数 | 意义 | 危险信号 |
|---|---|---|
| 摘要触发次数 / 周 | 压缩是否真的在跑 | 一直 0 = 门槛又设错了 |
| 每条摘要平均成员数 | 压得狠不狠 | 越来越大 = 主题在塌缩 |
| 撤销率 | 聚类判据好不好 | 高 = 压错了，判据要改 |

4. 与簇主题不一致的成员留在活跃，不出现在 `members` 里。
